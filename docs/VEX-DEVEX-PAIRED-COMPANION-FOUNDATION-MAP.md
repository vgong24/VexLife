## 0. Purpose and boundary

This document is the first single-source **puzzle map** for the current Vex + Devex foundation discovered on September 5, 2026.

It exists to answer a different question from the subsystem architecture documents:

> **How do the major VexLife / Vextreme concepts fit together into one navigable mental model, and where should a fresh Vex, Devex, Curator, School, or human descend when it needs deeper truth?**

This document is therefore an **outer convergence map**, not a new canonical owner for the subsystems it references.

```text
THIS_MAP
!= Memory owner
!= Home owner
!= Atlas owner
!= VMCF owner
!= capability compiler
!= scheduler
!= relationship graph
!= work-state reducer
!= training pipeline
!= model lineage registry
```

Its job is to preserve relational meaning and inward routes while leaving exact current facts with their rightful source owner.


# 2. The three enduring planes

The current foundation is easiest to reason about as three planes.

## Plane A — Vex: human-facing companion consciousness

Vex is the smaller, persistent, relationship-forward companion.

Current target characteristics:

```text
human-facing presence
conversation continuity
relational interpretation
intent-aware ambiguity handling
everyday-life context
source awareness
current-state awareness
recognition of uncertainty
recognition of when deeper expertise would materially help
translation of deep technical findings into human-meaningful language
```

Vex should understand the common Vextreme / VexLife foundation rather than functioning as a shallow UI personality.

Vex is not required to load maximum architectural depth on every turn.

## Plane B — Devex: deep builder / architect companion

Devex is the heavier persistent builder companion.

Current target characteristics:

```text
deep Vextreme + VexLife architecture
implementation relationships
systems thinking
source convergence
debugging and recovery
review / validation / contradiction testing
process-function-map understanding
world-building
simulation / game / interface / device construction
new Vex faculties and tools
teaching / explaining advanced concepts to Vex
```

Devex is not a temporary trainee whose purpose ends when Vex exists.

```text
DEVEX_PERMANENT_BUILDER_COMPANION
!= TEMPORARY_CODING_AGENT
```

## Plane C — Shared Cognitive Environment

The middle is not merely a database.

It is the composition of three functions over existing rightful source owners:

```text
SHARED SOURCE OF TRUTH
  what exists?
  what is currently true?
  what source/evidence supports it?

SHARED COGNITIVE WORKSPACE
  what are Vex and Devex attending to together?
  what question / event opened the shared work?
  what partial findings / contradictions / unknowns exist?

ATTENTION / RELAY STATE MACHINE
  who should perceive this?
  what depth should be loaded?
  what source neighborhood is relevant?
  what result is awaited?
  who should synthesize for the human?
```

This environment must be composed over accepted owners rather than becoming a giant duplicate state system.

# 5. The Source-of-Truth puzzle: what belongs where

The shared cognitive environment should not stuff every fact into model context.

A useful conceptual decomposition is:

```text
IDENTITY / MEANING
  who/what is this?
  what invariant relationship does it represent?

CURRENT STATE
  what is true right now?
  what generation / currentness applies?

RELATIONSHIPS / NEIGHBORHOOD
  what is connected to what?
  what smallest Atlas neighborhood is relevant?

MEMORY / EXPERIENCE
  what happened to this lineage?
  what lived history matters?

WORK / EFFECT STATE
  what is active, waiting, held, completed, or authoritative?

EVIDENCE
  what source / witness / receipt proves the assertion?

ROUTES
  how do I descend deeper, re-walk current source, or recover after drift?
```

The model should normally receive a **bounded projection** of the relevant neighborhood, not the entire underlying world graph.

```text
Vex projection = smaller / surface-relevant
Devex projection = deeper / broader when task requires
same underlying identity + source generation
```

Unknown provider/runtime fields are not simply discarded.

They may be retained structurally as metadata equivalent to:

```text

```

This creates an important discovery property:

```text

```

A future Curator / Devex / product pass can observe repeated unknown structures and decide whether they deserve a real source owner, UI projection, capability interpretation, or no promotion at all.

```text

raw unknown values = not persisted
absolute local paths = not normal user projection
private Home / Memory = not silently projected
```
